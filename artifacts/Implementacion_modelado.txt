  Archivos a crear (3 archivos nuevos)

  1. src/operations/stages/modeling_stage.py

  Qué hace: Implementa la etapa "modeling" del orquestador. No contiene lógica
  de ML — solo invoca los CLIs existentes como subprocess.

  Flujo exacto:

  1. Sub-paso "base_models": Ejecuta secuencialmente 5 subprocess, uno por cada
  runner base. Cada uno genera sus predicciones_h{1,2,3,4}.csv en
  experiments/runs/{run_id}_{timestamp}/. Los comandos exactos (fielmente
  extraídos de los parametros_run.json oficiales y de FROZEN_EXECUTION_SPECS):

  E1: python -m src.modeling.runners.run_e1_ridge_clean
      --run-id E1_v5_clean --target-mode nivel --feature-mode corr
      --lags 1,2,3,4,5,6 --transform-mode standard
      --initial-train-size 40 --horizons 1,2,3,4
      --reference-run-id E1_v5_clean

  E2: python -m src.modeling.runners.run_e2_huber_clean
      --run-id E2_v3_clean --target-mode nivel --feature-mode corr
      --lags 1,2,3,4 --transform-mode standard
      --initial-train-size 40 --horizons 1,2,3,4
      --hypothesis-note prueba_sin_memoria_larga

  E3: python -m src.modeling.runners.run_e3_random_forest
      --run-id E3_v2_clean --target-mode nivel --feature-mode all
      --lags 1,2,3,4,5,6 --initial-train-size 40 --horizons 1,2,3,4

  E5: python -m src.modeling.runners.run_e5_catboost
      --run-id E5_v4_clean --target-mode nivel --feature-mode all
      --lags 1,2,3,4,5,6 --initial-train-size 40 --horizons 1,2,3,4
      --use-inner-tuning --iterations-grid 250,300
      --depth-grid 4,5 --l2-leaf-reg-grid 3.0,5.0
      --tuning-metric mae --inner-splits 3

  E7: python -m src.modeling.runners.run_e7_prophet
      --run-id E7_v3_clean --target-mode nivel --feature-mode corr
      --lags 1,2,3,4,5,6 --initial-train-size 40 --horizons 1,2,3,4
      --changepoint-prior-scale 0.2

  1. Cada comando usa context.run_command() que ya maneja cwd=ROOT_DIR, logging,
   y captura de stdout. El Python ejecutable se toma de
  STAGE_PYTHON["modeling"].
  2. Sub-paso "build_e9_table": Construye la tabla curada temporal para E9. Lee
  los predicciones_h{H}.csv recién generados de cada run, los mergea por fecha
  siguiendo la misma lógica que build_e9_curated_base_sheet (líneas 2801-2815
  del original), respetando E9_CANDIDATES_BY_HORIZON. Escribe un xlsx temporal
  en artifacts/tmp/tabla_e9_curada_{run_id}.xlsx con hojas E9_base_h1..h4.
  Estructura por hoja: fecha | y_true | {run_ids} | n_modelos_disponibles | 
  fila_completa | cobertura_modelos_fila.

  2. Para obtener y_true, lo lee del dataset maestro (los runners ya lo dejan en
   sus predicciones como columna y_true). La validación cruzada de y_true contra
   el dataset maestro (que hace load_curated_horizon_frame en E9) se mantiene
  porque E9 la ejecuta internamente al leer la tabla.
  3. Sub-paso "stacking_e9": Ejecuta E9 con los args congelados del benchmark
  operativo de riesgo:

  python -m src.modeling.runners.run_e9_stacking
      --run-id E9_v2_clean --meta-model huber
      --table-path {ruta_temporal_tabla_e9}
      --initial-train-size 12 --horizons 1,2,3,4
      --alpha-grid-size 40 --inner-splits 3
      --alpha-selection-metric mae --use-only-complete-rows
      --reference-run-id E1_v5_clean
      --extra-reference-run-ids E5_v4_clean,E3_v2_clean,E2_v3_clean,E7_v3_clean
      --hypothesis-note benchmark_operativo_riesgo_controlado
  4. Sub-paso "empaquetado_dual": Ejecuta el empaquetador dual con política
  9-1-9-1. Este será el script que creamos como clon del
  run_sistema_dual_operativo_radar.py.

  Outputs de la etapa: rutas de los runs generados, ruta del paquete dual.

  Riesgos identificados y mitigaciones

  1. Los run_ids se repiten entre ejecuciones. Cada runner crea un directorio
  {run_id}_{timestamp}, así que no hay colisión. Pero el grid de Excel sí
  sobreescribe filas con el mismo run_id. Mitigación: El orquestador usa run_ids
   operativos (OP_{week}_{run_id}) para no contaminar el grid experimental, o se
   acepta que re-correr con el mismo run_id actualiza la fila del grid (que es
  el comportamiento canónico del tracker).
  2. La tabla curada temporal debe ser xlsx con hojas nombradas exactamente 
  E9_base_h{1..4}. E9 lee pd.read_excel(table_path, 
  sheet_name=f"E9_base_h{horizon}"). Si la hoja se nombra diferente, falla.
  3. El dataset ML maestro debe existir antes de correr modeling. La nlp_stage
  ya valida esto y deja explícito si lo reutiliza o falla.
